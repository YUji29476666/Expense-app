# 支出管理アプリ 仕様書

## 1. 概要

留学生本人が自分の生活費を管理するためのモバイルアプリ。
「記録する」だけでなく、**日単位で使える額が分かる / 2通貨で感覚が掴める / 統計値と比較できる** の3点で差別化する。

- 想定ユーザー: 開発者本人（海外在住の学生）
- プラットフォーム: iOS / Android（Expo + React Native）
- 言語: 英語UI（将来的に日本語切替を検討）

## 2. 開発フェーズ

段階を分ける。当初は「Phase 1 を実機で1ヶ月使うまで Phase 2 に進まない」方針だったが、開発者の判断で Phase 2 に着手した。

| Phase | 内容 | バックエンド | 費用 |
|---|---|---|---|
| 1 | 手入力による記録・予算・日割り・2通貨・統計比較・分析 | なし（端末内で完結） | $0 |
| 2 | 写真・スクショ → AI自動入力（Gemini 3.1 Flash-Lite） | Supabase Edge Function（DBは端末内SQLiteのまま） | API従量課金 |
| 3 | 実ユーザーの匿名集計ベンチマーク | Supabase + 認証 | 従量課金 |

### Phase 1 を先に完成させる理由

- 費用ゼロで完結し、APIキーの管理も不要
- レシート読み取りは「入力を楽にする機能」であって、アプリの価値の中心ではない
- 実際に1ヶ月使ってみないと、どのカテゴリ分類が必要かは分からない

## 3. Phase 1 の機能

### 3.1 記録

- 支出・収入を手入力（金額 / カテゴリ / 店名 / メモ / 日付）
- カテゴリは初期値を用意し、ユーザーが追加・編集・削除できる
  - 初期カテゴリ: Rent, Food (Groceries), Food (Eating out), Transportation, Utilities, Phone/Internet, Education, Health, Entertainment, Clothing, Remittance/Fees, Other
  - 海外生活特有の項目として **Remittance/Fees**（送金手数料・為替手数料）を必ず含める
  - 収入カテゴリ: Scholarship, Part-time job, Internship（入力画面で Income 選択時のみ表示。Other は両方に表示）
- 同じ店名を入力したとき、前回のカテゴリを候補として提示する（学習は単純な頻度カウントでよい。AI不要）

### 3.2 今期の残り予算（差別化の中心）

月末に反省するのではなく、記録するたびに今期あといくら使えるか分かるようにする。

- ホーム画面の最上部に **「This month you can spend」（今期使える残り額）** を大きく表示
- 計算式:
  ```
  this_month_can_spend = 月予算 - 今期のここまでの支出
  ```
- 収入は残り予算に加算しない（収支は Analytics で確認する）
- 残りが月予算の 20% を切ったら黄、マイナスになったら赤で表示する
- 「月予算」は固定額。カテゴリ別予算も別途設定できる

### 3.3 2通貨併記

- 通貨は **USD（表示）→ JPY（母国）固定**。JPY → USD は選択肢に出さない
- 金額は常に両方を表示する。例: `$12.40 (¥1,860)`
- レートの扱い:
  - [frankfurter.app](https://frankfurter.app)（APIキー不要・無料）から取得するボタンで設定する（手動入力は廃止）
  - レート未設定のときは取引を保存させない
  - **取引ごとに、その時点のレートをレコードに保存する**（`rate_used`）。後からレートが変動しても過去の記録の円換算額がブレないようにする
  - 通信失敗時は最後に取得したレートを使い、画面に「最終更新日」を出す

### 3.4 予算アラート（ルールベース、AI不要）

以下は全て単純な計算で実装する。API呼び出しは行わない。

- 「Food がカテゴリ予算の 80% に達しました」
- 「先月の同時点より $X 多く使っています」

文言はテンプレートで持ち、閾値は定数として1ファイルにまとめる（後から調整しやすくする）。

### 3.5 統計値との比較

**実ユーザーの集計ではなく、公開統計を内蔵する。**

- `assets/benchmarks.json` に、地域 × カテゴリの月額目安を持たせる
- 設定で自分の地域を選ぶと、その基準値と自分の支出を比較する
- 画面には必ず **出典名と調査年度** を表示する（例: "Source: XXX Survey, 2025"）
- 断定を避ける表現にする。「平均より15%高い」ではなく「この調査の平均値より15%高い」
- データが無い地域を選んだ場合は比較を非表示にする（推測値を出さない）

> 実装時の注意: 具体的な統計値は開発者が信頼できる出典（大学の生活費見積もり、公的な家計調査など）から手で入力する。AIに数値を生成させてはいけない。

### 3.6 分析画面

- 当月のカテゴリ別内訳（円グラフまたは横棒）
- 直近6ヶ月の推移（折れ線または縦棒）
- カテゴリを選ぶと、その明細一覧に遷移
- 収入と支出の差額（今月の収支）

## 4. データ設計

### 4.1 保存方式

`expo-sqlite` を使う。AsyncStorage は使わない（集計クエリが必要なため）。

### 4.2 金額の扱い（重要）

**金額は必ず整数（最小通貨単位）で保存する。** 浮動小数点で持つと、合計値が 1 セントずれる不具合が必ず発生する。

- `$12.40` → `1240`（USDは100分の1）
- `¥1860` → `1860`（JPYは補助単位なし。通貨ごとの exponent をテーブルで持つ）
- 表示時のみ小数に変換する

### 4.3 テーブル

```
transactions
  id              TEXT PRIMARY KEY
  type            TEXT      -- 'expense' | 'income'
  amount_minor    INTEGER   -- 現地通貨、最小単位
  currency        TEXT      -- 'USD'
  home_minor      INTEGER   -- 母国通貨換算、最小単位
  home_currency   TEXT      -- 'JPY'
  rate_used       REAL      -- 記録時のレート
  category_id     TEXT
  merchant        TEXT
  note            TEXT
  occurred_at     TEXT      -- ISO8601、日付単位
  created_at      TEXT
  receipt_uri     TEXT      -- Phase 2 用。Phase 1 では常に NULL

categories
  id                   TEXT PRIMARY KEY
  name                 TEXT
  icon                 TEXT
  color                TEXT
  budget_minor         INTEGER  -- NULL可
  sort_order           INTEGER
  is_archived          INTEGER

settings            -- 1行のみ
  display_currency    TEXT
  home_currency       TEXT
  monthly_budget_minor INTEGER
  month_start_day     INTEGER   -- 1〜28。給料日基準の月区切りに対応
  region_code         TEXT      -- ベンチマーク用
  last_rate           REAL
  last_rate_at        TEXT
```

`month_start_day` を持たせる理由: 学生は月初ではなく仕送りや給料の日を起点に考えることが多い。1日固定にすると使いづらい。

## 5. 画面構成（Expo Router）

```
app/
  (tabs)/
    index.tsx          Today  — 今期使える残り額、今日の記録、クイック追加
    transactions.tsx   History — 日付でグループ化した一覧、検索・フィルタ
    analytics.tsx      Analytics — 内訳、推移、ベンチマーク比較
    settings.tsx       Settings — 通貨、レート、予算、カテゴリ、地域
  transaction/
    new.tsx            記録追加（モーダル表示）
    [id].tsx           記録の編集・削除
  category/
    index.tsx          カテゴリ管理
```

### 入力画面の要件

記録が面倒だと続かない。ここは特に作り込む。

- 開いた瞬間に数字キーパッドにフォーカスが当たっている状態にする
- 日付の初期値は今日
- カテゴリは最近使った順に上に並べる
- 保存後はモーダルを閉じ、ホームの「This month you can spend」が即座に更新される

## 6. 技術方針

- TypeScript。`any` を使わない
- 状態管理: 最初は React の state と Context のみ。ライブラリは必要になってから入れる
- グラフ: `victory-native` または `react-native-gifted-charts`。導入前に Expo SDK 57 との互換を確認する
- 日付処理: `date-fns`
- **Phase 1 では外部APIを呼ばない。** 例外は為替レート取得（frankfurter.app）のみ
- ディレクトリ構成:
  ```
  src/
    db/          スキーマ、マイグレーション、クエリ
    domain/      金額計算、日割り計算、アラート判定（純関数。UIに依存させない）
    components/  再利用するUI
    hooks/
    constants/   カテゴリ初期値、閾値、通貨定義
  assets/
    benchmarks.json
  ```
- `domain/` は純関数だけで構成し、テストを書く。金額計算と日割り計算のバグは信用を失う中核部分なので、ここだけはテストを必須にする

## 7. やらないこと（Non-goals）

明示的に対象外とする。判断のブレを防ぐため。

- 銀行口座・カードの自動連携（Plaid等）— 費用と審査負担が個人開発の規模を超える
- 複数ユーザーでの共有・割り勘
- 投資・資産管理
- Edge Function を経由しない外部AI API 呼び出し
- Phase 2 での SQLite → Supabase DB 移行（8章の判断記録を参照）
- レシート画像のクラウド保存（Phase 2 でも端末内に留める）

## 8. Phase 2 以降（着手時に詳細化）

### Phase 2: 写真・スクショからの自動入力

- `expo-image-picker` でカメラ撮影、またはライブラリから写真・スクリーンショットを選択
- 送信前に端末で縮小・圧縮する（通信量と API 費用を抑える）
- 画像は Supabase Edge Function に送り、そこから **Gemini 3.1 Flash-Lite**（画像入力）を呼ぶ
  - **APIキーは Edge Function の secrets に置く。アプリ側には絶対に置かない**（アプリのバイナリからは誰でも文字列を抽出できる）
  - Gemini には JSON スキーマ指定の構造化出力で返させ、Edge Function 側でも検証してから返す
- 抽出するのは 種別（支出/収入） / 金額 / 通貨 / 店名 / 日付 / カテゴリ候補
- 最初は **1枚 → 1取引**。1枚に複数取引があるスクショ（明細一覧など）への対応は後で検討する
- 金額は Edge Function からは表示単位（例: 12.40）で受け取り、端末の `domain/` で最小単位の整数に変換する
- 取引の `rate_used` は読み取り結果ではなく、これまでどおり保存時点の設定レートを使う
- 結果は必ず**確認画面に出して、ユーザーが直せるようにする**。自動保存はしない
  - 読み取り結果は「Add transaction」のフォームに入力済みの状態で表示し、上に「Filled from image — check each field, then save.」と要確認点を出す
  - 要確認点: 金額なし / 日付なし（今日で代用）/ カテゴリなし / 通貨表記なし（表示通貨とみなす）/ 母国通貨（JPY）のレシート
  - JPY のレシートは現在のレートで USD に換算して入れ、元の金額とレートを表示する。レート未設定なら金額は空欄のまま
- 読み取り失敗時は手入力にフォールバック
- 1枚あたりのAPI費用を把握し、月間上限を設定画面に持たせる
- Edge Function の URL と anon key は公開されるため、悪用で API 費用が膨らまないよう3層で守る
  1. Google Cloud 側の割り当て（1日のリクエスト数）と予算アラート — 確実な上限
  2. Edge Function 内の回数制限（IP ごとに 5回/分・30回/時、インスタンス全体で 60回/分、超過は 429）— メモリ上のため補助
  3. アプリ内の月間上限（設定画面）— 正規アプリからの使いすぎ防止
  - あわせて画像サイズ上限（約3MB）を Gemini に送る前に確認する

#### 判断記録: SQLite を Supabase DB に移行しない

画像読み取りに必要なのは「APIキーを隠して Gemini を呼ぶ中継役」だけで、取引データの置き場所は関係ない。Supabase は Edge Function のためだけに使い、DB は端末内 SQLite のまま残す。

| 観点 | SQLite のまま + Edge Function | Supabase DB に移行 |
|---|---|---|
| コード変更 | Edge Function と読み取り画面の追加だけ | 全クエリ・マイグレーション・テストの書き直し |
| オフライン | 記録・集計はオフラインで動く（読み取りだけネット必須） | ネット必須、またはオフライン同期の実装が必要 |
| 認証 | 不要 | 必須（行単位のアクセス制御 RLS も必要） |
| 費用 | Edge Function の無料枠内に収まる見込み | DB 容量・転送量も課金対象 |
| 複数端末・Phase 3 | 未対応 | 対応できる |

複数端末での同期や Phase 3 の匿名集計が必要になった時点で、改めて移行を検討する。

### Phase 3: 実ユーザーのベンチマーク

- ユーザー認証と同期が前提。Phase 1・2 のデータをサーバーへ移行する設計が必要
- プライバシー: 同条件のユーザーが **N人（例: 20人）未満のときは比較を表示しない**。少人数だと個人が特定されうるため
- 送信するのはカテゴリ別の月額合計のみ。店名・メモ・日付の詳細は送らない
- 集計に使うことをオンボーディングで明示し、オプトアウトできるようにする

## 9. 完成の定義（Phase 1）

以下すべてを満たしたら Phase 1 完了とする。

- [ ] 実機（Expo Go）で支出・収入を追加・編集・削除できる
- [ ] アプリを再起動してもデータが残っている
- [ ] 「This month you can spend」が正しく計算され、記録すると即座に更新される
- [ ] 全ての金額が2通貨で表示される
- [ ] カテゴリ別予算の超過アラートが出る
- [ ] 分析画面に当月の内訳と6ヶ月推移が表示される
- [ ] ベンチマーク比較に出典が表示されている
- [ ] `domain/` の計算関数にテストがあり、全て通る
- [ ] 開発者本人が実際に1ヶ月間、これで家計を記録できた
